## 効果の確かめ方

本編の「次にどう確かめるか」では、次の 4 つを決める。
この節は、レポートを踏まえて発表者がまとめた**実践案**。レポートが直接示した手順ではない。

{.tight}
| 項目 | 問い | 例（AGENTS.md に規約を追記） |
| --- | --- | --- |
| 狙う成果 | 何を良くしたいか | 同じ指摘の繰り返しを減らし、人のレビューを設計の議論に使う |
| 近い観測 | 変更の影響を早く確かめられるものは何か | 同種の変更での、その違反の再発 |
| 悪化の確認 | 損ねたくないものは何か（品質・負担・コストなど） | 人の確認の負担、別の規約違反、重要な指示が埋もれること |
| 見直す時期 | いつ判断するか | 2 週間後 |

{pause up}

## 測るときの注意

- 体感は開発者体験を捉える大事な情報（DORA の調査でも、能力や成果の多くを回答者の自己申告で測定している）。
  ただしチームの改善を判断するには、作業の観測を組み合わせる
- 変更前の状態と、比較する範囲を先に決める
- 比較の単位をそろえる。例：PR を分割したら、PR 単位の待ち時間だけでなく、必要な変更全体が終わるまでの時間と手戻りも見る
- 本編の AGENTS.md の例なら、対象になった PR の数も記録する。人の確認を一部残す。変更の種類の違いを考慮する。
  厳密な因果推定までは求めない

{pause scroll}
- デリバリーの改善なら、速さと安定性をセットで見る
- ただし 7 能力すべてをその二軸だけで評価すると、ユーザーへの価値や開発者体験が抜け落ちる
- PR の行数やコミット頻度は、能力を捉える補助情報。それ自体を目標にしない
- ロールバックの回数は、手元の試行錯誤と、本番障害への対応とで意味が違う。分けて扱う
- [DORA Quick Check](https://dora.dev/quickcheck/) は、5 指標の現在地を定期的に確かめる用途向け。
  5 指標は能力の改善に遅れて動くので、2 週間程度の小さな実験の効果を測る用途には向かない（Appendix A）

{pause up}

## 使った量ではなく、成果を見る

DORA Insights「Finding balance in the era of tokenmaxxing」（Evan Conaway, 2026-06-02）より。
トークン消費量のランキングで AI 活用を促す「tokenmaxxing」への警告。

{.credit}
<https://dora.dev/insights/finding-balance-in-the-era-of-tokenmaxxing/>

{.block title="記事が挙げる問題" pause scroll}
> - トークン消費量は、かつての「コード行数」と同じ見かけだけの指標。指標を目標にすると、指標として機能しなくなる（グッドハートの法則）
> - 個人ランキングは、知識の抱え込み・雇用不安・燃え尽き・見せかけの生産性を招く
> - 記事は外部文献（Masood）を引いて、予算が最も大きいチームでもコスト 10 倍に対しスループットの伸びはわずか、と紹介している

{.block title="記事が挙げる代わりの方法" pause scroll}
> - 個人や全社ではなく、**チーム・アプリケーション・用途**の単位で利用を見る
> - DORA の指標を、**受け入れられた変更 1 件あたりのコスト**と**コードの手戻り率**と組み合わせる
> - ランキングの代わりに利用状況のダッシュボードを置き、使いすぎを止める仕組み（circuit breaker）を設ける
> - AI Capabilities Model の能力（利用方針の明確化、ユーザー中心、内部プラットフォームへの投資など）に投資する

{.remark pause scroll}
記事は利用量の追跡を全否定してはいない。普及の初期に試行を促す目的なら意味がある、としている。
ただし、使った量は成果が出たかどうかの代わりにならない。悪化の確認には、コストの増え方も入れておく。

{pause up}

## J カーブ：最初は下がることがある

ROI レポートは、導入初期に価値が一時的に下がりうることを、**J カーブ**という概念モデルで説明している。（ROI pp.8–10）

{.tight pause scroll}
| 要因 | 内容 |
| --- | --- |
| 学習コスト | 新しい使い方を覚え、ワークフローを組み替える時間 |
| 検証の負荷 | 生成されたコードを確かめる時間。生成量が増えるほどレビューの負担も増える |
| パイプラインの適応 | テストや承認などの下流が、増えた量に追いつくまでの調整 |

{.block title="レポートの説明" pause scroll}
下がり方の深さや期間は予測できない。学習の段階を失敗と誤解して投資を引き上げるのが、取り組みが失敗する典型。（ROI pp.8, 10）

{.block title="本資料の提案" pause scroll}
下がったことだけで失敗と判断しない。**見直す時期と、改善の兆候を先に決めて**観察する。

{pause up}

## 事例で 1 周する

場面：AI に書かせた PR が大きくなり、レビューが滞る。

{.tight pause scroll}
| 手順 | 内容 |
| --- | --- |
| 原因の仮説 | 独立した複数の変更が 1 つの PR に入っている（ほかに、担当者の不足、文脈の不足なども考えられる） |
| 関係しそうな能力 | 小さいバッチ単位の作業 / 優れたバージョン管理プラクティス |
| 試す変更 | レビューできる変更ごとに分けて、エージェントに作らせる |
| 狙う成果 | レビュー待ちを短くし、必要な変更全体を早く終える |
| 近い観測 | PR あたりの変更行数（小さくできたか）、レビュー開始までの時間 |
| 悪化の確認 | 差し戻し・不具合が増えていないか |
| 比較の単位 | 同程度の変更内容で、変更全体が終わるまでの時間と手戻りも見る |
| 見直す時期 | 次のスプリント末 |

{.remark pause scroll}
同じ「レビュー待ち」という症状でも、原因によって改善案は変わる。
ここでは変更の大きさを原因と仮定して小さいバッチ化を試し、確かめる。
